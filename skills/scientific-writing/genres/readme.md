# Genre: README

**Reader**: a developer who arrived from a search or a link, knows the
field's everyday tools, and decides within a screen whether to read on.

**Assumed**: the language, the package manager, git. **Defined**: every
name the project coined, at first use -- or the name stays out of the
README.

The ledger has one row per section, and its claim is the question that
section answers.

## Rules

- **The opening answers Heilmeier questions 1 to 4** with no jargon:
  what it is, what it is good for and for whom, and what is new about
  it. Then how to use it. A coined name or file path before those
  answers is a reader lost.
- **Order by falling interest**: what it is, why it matters, how to use
  it; then installation detail; then how to contribute. A reader who
  stops anywhere leaves with what they came for.
- **Lead with the strongest contributions**, each stated as what the
  reader gets, with one concrete instance as its evidence: a number, a
  before and after. Features ordered by file are an index, not a pitch.
- **Altitude.** Per-file rationale, internals and the history of a
  decision go behind a link -- a layout document, the code's docstrings.
  The README links to the index of the repo; it is not that index.
- **Commands are copy-pasteable**, one block per platform, named.
- **Heilmeier questions 5 to 8** -- risks, cost, schedule, exams -- do
  not belong.

## Budgets

- The first screen, about 25 lines, answers what and why.
- A feature bullet: at most three sentences.

Written against this repo's own README (6,276 words, 735 lines): an
introduction and feature list in the first 70 lines, a file-by-file
index in the last 380. Its owner judged it "far too long, dense", with
"too many low-altitude details".
